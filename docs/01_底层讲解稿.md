## 第一部分：3 分钟自我介绍 + 项目概述（开场）

面试官你好，我是石志豪，中科院大学计算机技术硕士在读，方向是模式识别与机器学习。我求职的方向是 AI Agent 应用开发，技术栈是 LangChain、LangGraph、RAG、MCP 和 FastAPI。

我在中科院沈阳高精数控做 AI Agent 应用开发实习生，独立负责了一个「数控 XML 界面生成与自动部署 Agent」的完整后端。这个项目的业务背景是：数控机床的操作界面是用工业 XML 配置的，以前要靠工程师手工写，一个界面要写几百行、还得懂数控变量绑定规则，很慢也容易出错。我做的东西，就是让操作工用一句自然语言——比如「顶部显示主轴转速，左侧放个启动按钮」——就能自动生成合法、可部署的 XML 界面。

我独立负责的模块有六个：一是用 FastAPI 加 Python asyncio 搭的异步后端；二是用 LangGraph 的 StateGraph 做整个 Agent 的状态编排；三是 LangChain 的结构化输出、Tool Calling，以及用 MCP 协议封装工具服务；四是用 Chroma 向量库建 RAG 知识库，存 XML 语法、数控控件、绑定规则这三类知识；五是用 Qwen2.5 做基座，用 PEFT 加结构敏感的 LoRA 微调来适配工业 XML 生成；六是工业 XML 片段生成和结构约束校验这两个模块。数控硬件底层部署和前端不是我做的，我只保留占位。

这个项目让我真正把「LLM 的不确定输出」关进了一个「确定性的工程框架」里——这是我觉得最有价值的地方，接下来我想从最底层开始，把整套技术是怎么一环扣一环串起来的讲清楚。

## 第二部分：完整底层逻辑串讲

### 1. 大模型底层原理：为什么 LLM 会「胡说」

我先从一个最根本的问题讲起：**大模型到底是什么、它为什么需要后面这一整套东西。**

GPT、Qwen 这类模型的本质，是一个**自回归的概率模型**。它做的事情只有一件：给定前面所有的 token，预测下一个 token 的概率分布，然后采样一个出来。所谓「生成」，就是把「预测下一个 token」这件事重复几万次。这里有两个关键点，直接决定了后面每一个技术选择的动机：

第一，**它是在「补全」，不是在「查事实」**。它学的是训练语料里 token 与 token 之间的统计关联，而不是一个可以检索的事实库。所以它对自己没见过的、私有的、会变的知识，只能「编」——这就是幻觉的根源。

第二，**它的输出是「采样」出来的，带有随机性**。temperature 越高越随机。这带来两个问题：一是同样的问题两次答案不一样；二是对于 XML 这种有严格语法结构的东西，随机性会让它生成「标签不闭合」「引号不匹配」这种结构错误。

理解了这两点，后面所有技术就都有了因果：因为「会编」，所以需要 RAG 给它注入事实；因为「采样随机」，所以需要压低温度 + 结构化输出约束 + 微调来让它「守结构」。这是整条链路的起点。

### 2. 微调（PEFT / LoRA 底层）：怎么让它「更会写 XML」

既然通用模型的输出不够「结构敏感」，第一反应是微调。但**全参数微调 7B 模型要几十 G 显存，我实习生根本拿不到这个资源**，这就引出了 PEFT。

PEFT 的核心思想是**冻结原模型，只训练一小撮新参数**。而 LoRA 是其中最经典的：它基于一个假设——**大模型在下游任务上的「增量更新」是低秩的**。也就是说，微调需要的权重变化 ΔW，可以用两个小矩阵 A 和 B 的乘积来近似，ΔW = B·A，其中 A、B 的秩 r 远小于原权重维度。这样 7B 模型的微调，可训练参数能压到原来的千分之一，显存和训练成本都降下来了。

但我在这里做了一个**针对性改进**，也是这个项目我认为最有区分度的地方：**结构敏感 LoRA**。普通的 LoRA 只优化「语义」，它对所有 token 一视同仁。但对工业 XML 来说，`<`、`>`、`</`、属性名这些**结构 token 错一个，整段就解析不了**，后果比一个内容词错了严重得多。所以我在训练 loss 上做了**按 token 类型加权**：给这些结构符号位置乘一个更大的权重（比如 2 倍），相当于告诉模型「这些符号你更不许错」。这本质是在用 loss 重加权的方式，把「结构正确」这个业务约束，直接编码进训练目标里。

> 这里可以展开的底层点：LoRA 的 rank r 是「表达能力」和「可训练参数量」的 trade-off，r 越大越接近全参微调；alpha/r 决定更新幅度；target_modules 决定哪些层被适配（attention 投影 + MLP）。

### 3. 结构化输出问题：从「自由文本」到「可消费的契约」

微调解决了「风格」，但还有一个工程问题：**LLM 输出的是自由文本，下游代码没法稳定地解析它**。如果我让模型「用自然语言描述一下你识别出了哪些控件」，我后面拿到的是一段无法可靠提取字段的话。

解法是**结构化输出**：让模型直接输出 JSON，并且我用 Pydantic 定义一个严格的 schema，比如 `RequirementParse`，里面 `items` 是一个 `RequirementItem` 列表，每个 item 有 `widget`、`control_kind`（枚举）、`binding` 这些字段。模型输出后我用 `model_validate` 强制校验，**非法就直接报错触发重试**，而不是让它蒙混过关。

这里有个关键 trade-off 要讲：**结构化输出是有代价的**。约束 JSON 格式会消耗更多 token、降低一定的灵活性，而且模型仍然可能输出「语法上合法、语义上错误」的 JSON（比如把只读变量绑给了输入框）。所以结构化输出不是终点，它只是把「解析确定性」这个环节接住了，**语义正确性要靠后面的 RAG 注入规则 + 校验模块来兜底**。这正好引出下一层。

### 4. RAG 底层：向量、Embedding、检索原理

结构化输出保证了「格式对」，但「内容对」怎么办？XML 语法、数控控件规范、变量绑定规则，这些是**私有、专业、会更新**的知识，LLM 训练数据里没有，我也不能全塞进 prompt——一是会爆上下文窗口，二是知识一更新就得改 prompt 重发版。

所以用 RAG。RAG 的底层我拆成三步讲：

**第一步，Embedding**。把一个文本片段映射成一个高维向量（我用的 bge-small-zh，512 维）。它的核心性质是：**语义相近的文本，向量在空间里离得近**。这是「语义检索」能成立的全部基础。我为什么选 bge-small-zh：一是中文语义检索效果好，二是维度小检索快，三是能本地跑、不依赖外部 API。

**第二步，向量检索**。拿到用户的查询，也 Embedding 成向量，然后在向量库里找最相近的 top-k。这里有个底层细节：**暴力遍历所有向量算余弦相似度是 O(n) 的**，知识库大了会慢。所以我用的 Chroma 底层是 **HNSW 近似最近邻索引**——它构建一个多层图结构，检索时贪心地在图上跳转，把复杂度降到接近 log 级，代价是「近似」而不是「精确」，牺牲一点点召回率换速度。这是典型的「用近似换性能」。

**第三步，相似度度量**。我用的是余弦相似度（归一化后的内积）。这里可以展开一个面试常问点：**为什么用余弦而不是欧氏距离**——因为文本向量往往很稀疏、长度差异大，欧氏距离会被「向量长度」干扰，而余弦只关心「方向」，对语义更鲁棒。

最后讲**为什么选 Chroma 而不是 FAISS**，这是个高频追问：FAISS 的强项是**纯检索性能**，尤其是大规模、GPU 加速场景，但它本质是个「索引库」，增删改麻烦，要自己管持久化和元数据。而我的场景是：**知识库不大，但知识会频繁更新**（绑定规则、控件规范会迭代）。Chroma 自带持久化、增量 upsert、元数据过滤，工程上省事得多。所以结论是：**规模大、知识静态 → FAISS；规模适中、知识动态 → Chroma**。这是我在权衡后做的选择，不是随便选的。

### 5. Tool Calling 底层：让模型「提出动作」而不是「执行动作」

知识注入了、XML 生成了，但 Agent 还要能**改变外部世界**——去部署。这就要工具调用。

Tool Calling 的底层本质，很多人理解错了。它**不是**「模型自己去调函数」，而是：你给模型一份**工具的 JSON Schema 描述**（工具名、参数、描述），模型在需要的时候，输出一个结构化的「调用意图」——`{tool_name, arguments}`，**真正的执行是宿主代码拿到这个意图之后去做的**。

这个「模型只提意图、代码才执行」的解耦，是整个 Agent 安全性的根基。因为模型是不确定的、可以被 prompt 注入的，如果让它直接有执行权限，等于把一个不可控的东西接上了真实的数控设备。所以**决策和执行必须分离**。

### 6. MCP 工具封装：为什么要把工具做成「服务」

下一个问题：工具怎么管理和迭代？**如果每个工具都写死在 Agent 代码里，换一个工具就要改代码、重新发版**，这在工业现场很痛苦——数控设备的接口会随固件升级变化。

MCP（Model Context Protocol）解决的正是这个：它把工具抽象成**独立的外部服务**，通过统一的 JSON-RPC 协议暴露，Agent 端只需要配置一个服务地址。这样工具服务的增删改，**不影响 Agent 主流程**，这就是我需求里说的「支持配置迭代」。MCP 底层的两个核心动作是 `tools/list`（动态发现有哪些工具）和 `tools/call`（调用某个工具）。

我在项目里封装了一个 MCP 客户端，并把「部署」这个工具通过 MCP 暴露。这里有个安全设计要强调：**部署是危险操作**，所以工具本身带了一个 `confirmed` 参数，必须为 true 才会真正下发，而这个确认来自图里的「人工确认节点」——这是 human-in-the-loop 的落地。

### 7. LangGraph 状态机底层：把控制流显式化

现在组件齐了（解析、检索、生成、校验、部署），但**怎么把这些串起来、处理分支和重试**？

如果手写代码，就会是「if 需求不清 → 澄清；elif 校验失败 → 重生成」这样一堆嵌套 if/else，散落在各个函数里，改一处漏一处，而且**没法直观看到完整流程**。LangGraph 解决的是这个：它把业务流抽象成一张**图**——节点是「一步处理」，边是「条件转移」，整个 Agent 就是一个**显式的有限状态机（FSM）**。

底层上，LangGraph 维护一个**共享状态 State**（我用 Pydantic 定义），它在节点间流动；每个节点读 State、改 State、返回更新；条件边根据 State 的某个字段决定下一步去哪。这个设计的价值有三点：一是**控制流显式可见**，可读可测；二是**支持 checkpoint**，状态可以序列化存下来，实现「断点续跑」和「人工暂停后恢复」；三是**循环是有界的**——我的「校验失败 → 回炉重生成」不是 `while True`，而是通过 `retry_count` 上限和 `recursion_limit` 来兜底，超过就强制终止或上升人工。这是生产级 Agent 和 demo 的分界线。

### 8. LCEL 链式编排：小步骤的可组合性

在 LangGraph 的节点内部，具体到「一个节点里可能要串几件事」（比如检索节点里「构造查询 → 检索 → 过滤去重」），我用 LangChain 的 LCEL（LangChain Expression Language）来组合。

LCEL 的底层思想是**用管道把 Runnable 串起来**：`prompt | llm | output_parser`。它的价值在于：一是**声明式**，把「数据怎么流」写清楚；二是**自动支持异步、批处理、流式**——你用 `|` 连出来的链，天然能 `ainvoke` 异步调用，这对 asyncio 后端很重要；三是**可复用**，每个环节是一个独立的 Runnable，可以单独测试、单独替换。

这里我要讲一个清醒的认知，也是面试官爱问的：**LCEL 适合「线性的、无分支的小链」，一旦出现复杂分支、循环、状态依赖，就该让位给 LangGraph**。两者不是竞争关系，是「链内用 LCEL 组合步骤，链外用 LangGraph 编排控制流」的分层。

### 9. asyncio 异步底层：为什么 Agent 后端必须异步

上面所有东西都要跑在一个服务里，那为什么必须是异步？因为 **Agent 链路的瓶颈在 IO，不在 CPU**：一次 LLM 调用几百毫秒到几秒，向量检索也有延迟，这些时间里 CPU 是空等。

如果用传统的同步模型（一个请求一个线程），线程池很快就会被这些「空等的 IO」占满，并发一上来就崩。asyncio 的思路是**单线程 + 事件循环**：代码在 `await` 一个 IO 的时候，主动让出控制权，事件循环去处理别的任务，IO 完成了再回来继续。这样**一个线程就能扛成千上万个并发 IO**。

这里有个底层概念要讲清楚：**asyncio 是「协作式」的，不是「抢占式」的**。它只会在 `await` 处切换，如果一个任务里写了阻塞的 CPU 密集计算（比如一个大循环算向量），整个事件循环都会被它卡死。所以生产上要「IO 用 async，CPU 密集用线程池/进程池隔离」。我在项目里的 LLM 调用、向量检索、MCP 调用全部是 `await` 的，保证事件循环不被阻塞。

### 10. FastAPI 后端服务：把 Agent 暴露成 HTTP 服务

最后，用 FastAPI 把这套 Agent 暴露成 HTTP 服务。FastAPI 底层基于 ASGI（异步服务器网关接口）+ Starlette，它和 asyncio 是天然衔接的：**路由函数声明成 `async def`，FastAPI 就把它们投进事件循环里跑**，这样 Agent 链路的异步优势能一路贯穿到 HTTP 层。

我在服务里做了几件「生产化」的事，也是面试可以讲的：一是**trace_id 贯穿**——每个请求生成一个 trace_id，一路传到 Agent 链路，日志、工具调用记录都带这个 id，出问题能快速定位是哪一次请求、哪一步挂了；二是**启动时加载知识库构建索引**；三是把超时、重试、预算这些参数全部收敛到配置中心，用环境变量注入，**凭据绝不硬编码**。

### 11. 完整业务链路串联：把所有层拼起来

现在我把整条链路从用户输入到部署串一遍，这也是整个项目最完整的呈现：

用户输入一句自然语言 → **parse 节点**（Qwen 结构化输出，把需求解析成带类型、绑定变量的控件列表，这一步用到第 3 层的结构化输出和微调后的模型）→ 如果需求有歧义，走 `clarify` 节点反问用户 → **retrieve 节点**（用解析出的意图和控件名做 Embedding 检索，从 Chroma 召回语法、控件规范、绑定规则，第 4 层 RAG）→ **generate 节点**（结合解析结果 + 召回的知识，生成工业 XML 片段，第 2 层微调让它更守结构）→ **validate 节点**（三层校验：良构性 → schema → 业务绑定规则，第 6 层校验模块；不通过就回炉 generate，有界重试）→ **confirm 节点**（人工确认，human-in-the-loop）→ **deploy 节点**（通过 MCP 封装的受控部署工具下发，第 5、6 层的 Tool Calling + MCP）。这整个控制流，就是第 7 层 LangGraph 编排的，每一步的 IO 都是第 9 层 asyncio 异步，最后用第 10 层 FastAPI 暴露出去。

**这一串讲下来，每一层技术都是为了解决上一层的缺陷而引入的**：模型会编 → 引入 RAG；输出随机不守结构 → 引入微调 + 结构化输出；结构化输出只能保证格式对 → 引入知识注入 + 校验保证内容对；模型不能直接执行 → 引入 Tool Calling；工具难迭代 → 引入 MCP；控制流复杂易错 → 引入 LangGraph；IO 密集 → 引入 asyncio。这就是我理解这个项目的完整逻辑链。
