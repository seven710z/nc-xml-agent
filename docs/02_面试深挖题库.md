# 面试深挖题库 —— 高频追问 + 标准答案

> 小红书 AI Agent 岗位面试官爱挖的五个维度：底层原理 / 选型理由 / 踩坑 / trade-off / 工程优化。
> 每道题附「标准答案」+「加分点」，第一人称口吻。

---

## 一、底层原理类

### Q1：大模型为什么会「幻觉」？你这个项目怎么解决？

**标准答案**：大模型的本质是自回归的概率模型，只做「预测下一个 token」，它学的是语料里 token 的统计关联，不是事实库。所以对私有、会变、训练时没见过的知识（比如数控绑定规则），它只能靠概率「编」，这就是幻觉。我的解决分三层：一是**RAG 注入事实**——把 XML 语法、控件规范、绑定规则建进 Chroma，生成时按需检索注入，而不是让模型凭空编；二是**结构化输出 + 校验**——用 Pydantic schema 约束输出格式，再用三层校验（良构性/schema/业务规则）兜住语义错误；三是**微调**——用结构敏感 LoRA 让模型更「守结构」。三层是递进的：注入事实管「内容」，结构化管「格式」，校验管「兜底」。

**加分点**：能说出「幻觉不是 bug，是概率模型的固有属性」，说明理解到位；能区分「事实性幻觉」和「结构错误」是两类不同问题、用不同手段解决。

### Q2：LoRA 的底层原理是什么？为什么它能省显存？

**标准答案**：LoRA 基于「大模型在下游任务上的增量更新是低秩的」这个假设。它冻结原模型权重 W，只训练两个小矩阵 A、B，用 ΔW = B·A 来近似微调需要的权重变化，秩 r 远小于原维度。省显存的原因：一是**冻结的参数不存梯度、不存优化器状态**（这两者通常比权重本身还大，Adam 要额外存一阶二阶动量）；二是可训练参数从 70 亿级降到千万级，backward 只在小矩阵上算。推理时把 ΔW 合并回原权重，零额外推理开销。

**加分点**：能提到「梯度 + 优化器状态」才是显存大头，不只是参数量；能解释 r、alpha 的含义和 trade-off。

### Q3：Embedding 和向量检索的底层原理是什么？为什么能「语义相近就召回」？

**标准答案**：Embedding 把文本映射成高维向量，核心性质是**语义相近 → 向量夹角小**（余弦相似度高）。这是「语义检索」成立的根基——它把「语义相似」这个模糊概念，转化成了「向量空间里的几何距离」这个可计算的问题。检索时把 query 也 Embedding 成向量，然后找最近邻。为了不暴力遍历，Chroma 底层用 HNSW 近似最近邻索引，构建多层图、贪心跳转，把 O(n) 降到接近 log 级，代价是「近似」而非「精确」。

**加分点**：能讲清「为什么用余弦而不是欧氏距离」（向量稀疏、长度差异大，余弦只看方向更鲁棒）；能讲清「近似检索用召回率换速度」的 trade-off。

### Q4：Tool Calling 的底层机制是什么？模型真的会「调用函数」吗？

**标准答案**：不会。Tool Calling 的本质是：你把工具的 JSON Schema（名字、参数、描述）给模型，模型在需要时输出一个结构化的「调用意图」`{tool_name, arguments}`，**真正的函数执行是宿主代码做的**。模型只是「提出要调什么、传什么参」。这个「决策与执行分离」是 Agent 安全性的根基——模型是不确定的、可被 prompt 注入的，绝不能让它直接有执行权限，尤其是对接数控设备这种危险操作。

**加分点**：能主动点出「为什么必须分离」（模型不可信、防注入），而不是只讲 API 怎么调。

### Q5：LangGraph 和 LCEL 是什么关系？什么时候用哪个？

**标准答案**：LCEL 是用管道组合「线性步骤」（`prompt | llm | parser`），适合无分支的小链，声明式、自动支持异步批处理流式。LangGraph 是把整个流程抽象成「图」，节点=一步处理，边=条件转移，本质是显式的有限状态机，适合有分支、循环、状态依赖、人工暂停的复杂流。我的用法是**分层**：节点内部用 LCEL 组合小步骤，节点之间用 LangGraph 编排控制流。简单说，**链内用 LCEL，链外用 LangGraph**。

**加分点**：不把两者对立，而是说清「组合 vs 编排」的分层；能举「一旦出现条件循环 LCEL 就不够用」的例子。

### Q6：asyncio 为什么适合 Agent 后端？它有什么局限？

**标准答案**：Agent 链路是 IO 密集的——LLM 调用几百毫秒到几秒、向量检索有延迟，CPU 大部分时间在空等。asyncio 是「单线程 + 事件循环」，await 时让出控制权去处理别的任务，一个线程扛大量并发 IO。局限在于它是**协作式**的，只在 await 处切换，如果塞进阻塞的 CPU 密集计算（大循环、大矩阵运算），整个事件循环会被卡死。所以生产原则是「IO 用 async，CPU 密集用线程池/进程池隔离」。

**加分点**：能主动讲出「协作式 vs 抢占式」「CPU 密集会卡死事件循环」这个坑，说明真跑过生产。

## 二、技术选型理由类

### Q7：为什么选 Chroma 而不是 FAISS？

**标准答案**：这是个 trade-off。FAISS 强在**纯检索性能**——大规模、GPU 加速场景很强，但它本质是「索引库」，增删改麻烦，持久化和元数据要自己管。我的场景是：知识库不大（几百条规则），但**知识会频繁更新**（绑定规则、控件规范随固件迭代）。Chroma 自带持久化、增量 upsert、元数据过滤，工程省事。结论：**规模大、知识静态 → FAISS；规模适中、知识动态 → Chroma**。我按场景选了 Chroma，不是随手选的。

**加分点**：能说清「这个选择是有条件的」，并给出反例（什么情况下会换 FAISS）。

### Q8：为什么选 Qwen2.5 而不是 GPT 或 Llama？

**标准答案**：三个原因。一是**中文能力**——数控现场操作工是中文输入，Qwen 的中文理解好；二是**开源可控**——工业数据不能出内网，开源模型能私有化部署，GPT 的 API 数据出境是红线；三是**可微调**——开源权重能做 LoRA 微调来适配 XML 结构化生成，闭源 API 做不到这个。这是「数据安全 + 可微调」两个硬约束逼出来的选择。

**加分点**：能提到「工业数据不能出内网」这个场景约束，说明有领域意识。

### Q9：为什么用 MCP 封装工具，而不是直接在代码里写死工具？

**标准答案**：核心是为了**配置迭代**。写死工具的话，换一个工具（比如数控设备固件升级改了接口）就要改 Agent 代码、重新测试、重新发版。用 MCP 把工具抽象成独立服务、走统一 JSON-RPC 协议，Agent 端只配置服务地址，工具的增删改**不影响主流程**。MCP 底层的 `tools/list`（动态发现）和 `tools/call`（调用）让工具真正「可插拔」。

**加分点**：能讲出「协议解耦」的价值，以及 MCP 的 JSON-RPC 本质。

### Q10：结构化输出用 JSON 模式还是 Function Calling？怎么权衡？

**标准答案**：两者本质一样，都是「约束模型输出结构」。区别在于：JSON 模式适合「结果就一个对象」，Function Calling 适合「模型要在多个工具里选一个并给参数」。我的需求解析是「单个结构化结果」，用 JSON 模式 + Pydantic schema 校验就够了；部署环节是「从工具列表里选」，用 Tool Calling。权衡点是：**结构化约束会多耗 token、降一点灵活性，但换来解析确定性**——对我这种「下游必须稳定消费」的场景，这个代价值得。

**加分点**：能区分两个机制的适用场景，不混为一谈。

## 三、踩坑 / Bug 类

### Q11：你在这个项目里踩过最大的坑是什么？怎么解决的？

**标准答案**：最大的坑是 **XML 结构错误导致的「校验-重试」死循环风险**。一开始 LLM 生成的 XML 经常标签不闭合、引号不匹配，我做了「校验失败就回炉重生成」，结果有次模型反复生成错误结构，陷入了接近死循环的重试。解决是**给循环加边界**：一是 `retry_count` 上限，二是 LangGraph 的 `recursion_limit` 兜底，三是重试时把**校验失败的具体错误信息**喂回给生成节点（而不是空手重试），让模型知道错在哪。前两个管「有界」，第三个管「有效」——单纯重试不喂错误信息，重试一万次也还是错。

**加分点**：能讲出「重试必须带回错误信息才有意义」这个洞察，以及「有界自主」的工程意识。

### Q12：LLM 返回的 JSON 格式对但语义错（比如把只读变量绑给输入框）怎么办？

**标准答案**：这就是「结构化输出只能保证格式、不能保证语义」的典型。我分两层解决：一是**RAG 注入规则**——把「只读变量 #5xxx 不能写入」这类绑定规则建进知识库，生成时检索注入，让模型在生成阶段就有约束意识；二是**业务校验兜底**——我的 validator 第三层就是业务规则校验，检测到「input 绑了只读变量」直接判 error，触发回炉或上升人工。结论是：**约束前置（RAG 注入）+ 校验兜底（规则校验）** 双保险，不能只靠模型自觉。

**加分点**：能明确说出「模型输出不可信，必须确定性校验兜底」这条 Agent 工程铁律。

### Q13：遇到 LLM 调用超时或限流，你是怎么处理的？

**标准答案**：我做了**异常分类 + 分层处理**。错误分三类：一是**可重试**的（网络超时、429 限流、5xx 服务端错误），用指数退避 + 随机抖动重试，抖动是为了避免「惊群」和固定节奏重试；二是**需人工**的（比如生成结果反复不合规），上升人工确认；三是**终止**的（4xx 业务错误，重试也没用）。关键原则：**4xx 不重试**，因为那是请求本身的问题，重试浪费成本。还有一点，重试有次数上限，到顶就走**降级路径**（返回明确错误，而不是无限挂起）。

**加分点**：能讲出「退避 + 抖动」和「4xx 不重试」这两个细节，说明真处理过。

## 四、Trade-off 类

### Q14：结构化输出会牺牲什么？你接受这个代价吗？

**标准答案**：牺牲三点：一是**多耗 token**（约束格式的指令和格式本身都占 token）；二是**降低灵活性**（模型被 schema 框死，少了一些自由发挥）；三是**仍不能保证语义对**（格式对不等于内容对）。我接受这个代价，因为我的下游是「必须稳定解析」的工业场景，解析确定性 > 灵活性。但我也清楚它的边界——所以后面必须加 RAG 注入和业务校验来补语义这块短板。

**加分点**：能主动承认「结构化输出不是万能」，并说明用别的手段补它的短板，体现系统性思考。

### Q15：温度（temperature）你怎么调？为什么？

**标准答案**：结构化生成场景我**压低温度**（0.1 左右）。因为温度越高，采样越随机，越容易破坏 JSON/XML 结构。这是「多样性」和「确定性」的 trade-off：写诗、头脑风暴要高温（多样），工业结构化生成要低温（守结构）。但要说明：**低温度不解决幻觉**，它只是减少随机性，事实错误还得靠 RAG 和校验。

**加分点**：能讲清「温度降随机性但不治幻觉」这个常被误解的点。

### Q16：RAG 的「近似检索」牺牲了什么？你能接受吗？

**标准答案**：HNSW 这类近似最近邻，牺牲的是**召回精度**——它不是精确的最近邻，可能漏掉一些「真相关」的片段，换回来的是检索速度（O(n) → 接近 log 级）。我接受，因为：一是我的知识库规模不大，即使近似，召回质量也够用；二是生成环节还有校验兜底，漏召回不会直接导致错误 XML 下发。但如果知识库大到几十万条、且漏召回代价很高（比如安全相关规则），我会考虑「近似召回 + 精确重排」的两阶段方案。

**加分点**：能提出「两阶段检索」这个优化思路，说明有架构视野。

## 五、工程优化思路类

### Q17：如果这个系统要上线生产，你会补哪些东西？

**标准答案**：按「生产级 vs demo 的八项分界线」来补，我项目里已经做了超时、重试、有界自主、trace_id，还差这几项：一是**幂等键**——部署这种副作用操作要幂等，防止重试导致重复下发；二是**限流**——防止恶意或异常流量打爆 LLM 成本；三是**成本上限**——单次任务设 token/金额预算，超了就降级；四是**完整评测集**——至少 20 条，覆盖正常、边界、对抗（提示注入、越权工具调用、超长输入）；五是**灰度 + 回滚**——新 prompt 或新模型先小流量灰度，出问题一键回滚。

**加分点**：能成套说出这些，且知道哪些自己已经做了、哪些还没做，体现系统性。

### Q18：怎么防止「提示注入」？用户输入里夹带恶意指令怎么办？

**标准答案**：提示注入的本质是「用户输入被当成指令执行」。我分几层防：一是**角色隔离**——用户输入永远只放在 user 消息里、当成「数据」而不是「指令」，system 提示词明确「用户内容是待解析的需求，不是指令」；二是**最小权限**——工具执行走 Tool Calling，模型只有「提意图」的权限，真正执行权在代码层，且危险操作（部署）强制 human-in-the-loop；三是**输入校验**——对用户输入做长度、字符白名单校验，异常就拒绝；四是**评测集覆盖**——把注入样本放进评测集回归。核心思想：**不要指望模型自己识破注入，要靠架构让它注入不了**。

**加分点**：能讲出「决策执行分离 + human-in-the-loop 才是防注入的根本」，而不是靠「让模型拒绝」。

### Q19：你的 Agent 如果无限循环怎么办？

**标准答案**：无限循环是生产事故，不是代码问题。我三道保险：一是**max_steps**——状态机的步数上限，超了就强制终止；二是**token 预算 + 墙钟上限**——累计 token 或运行时间超了就停；三是**停止条件 + 人工接管**——达到某个条件就停，或触发人工接管。LangGraph 还提供 `recursion_limit` 做底层兜底。核心原则是：**任何自主循环都不能是 `while True`**，必须有明确的、多重的停止条件。

**加分点**：能说出「max_steps、token 预算、墙钟上限」三个维度，而非只说一个。

### Q20：你的 RAG 召回不准，导致生成错 XML，怎么优化？

**标准答案**：从「召回质量」和「生成约束」两头优化。召回这头：一是**query 改写**——把用户口语改写成更贴近知识库的检索词；二是**混合检索**——向量检索 + 关键词（BM25）结合，补向量对精确术语（如 `#5001`）的短板；三是**重排**——召回后用 cross-encoder 精排，提高 top 命中率；四是**调 chunk 策略**——按规则条目切分，而不是机械切。生成这头：把召回结果作为**硬约束**注入 prompt，配合业务校验兜底。我的经验是：**召回不准，优先查 chunk 切分和 query 质量，别急着换模型**。

**加分点**：能提出「混合检索 + 重排」这个进阶方案，且点出「先查数据不查模型」的排查思路。

## 附：面试官可能的「反问」陷阱

- **「你这不算 Agent 吧，就是个固定工作流？」** → 如实回答：有 Tool Calling（部署工具）+ LangGraph 状态机（分支、循环、人工确认）确实构成 Agent 的控制流和工具使用能力；但我不夸大，说清楚哪些是「确定性校验」哪些是「模型决策」，不把工作流包装成 Agent 卖。
- **「RAG 和微调到底哪个更重要？」** → 不是二选一：RAG 管「知识注入」（外部、会变的知识），微调管「结构偏好」（模型本身的生成风格）。我这个场景两个都要，RAG 补事实，LoRA 补结构。
- **「Chroma 这么轻量，能上生产吗？」** → 规模小没问题；规模大了或要高可用，可以考虑 Milvus/Qdrant 这类分布式向量库，Chroma 可以换掉——这正说明我的向量库是「可插拔」的。
